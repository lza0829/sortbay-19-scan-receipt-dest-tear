# ADR-001：缺目的地过机装载的正确性口径

## 背景
分拣线过机时条码可能缺目的地码。旧实现把缺码件照样插成「待路由」，导致：
装载回执亮成功、扫描册无拒因、待路由桶与总览待路由虚涨却无法裁决、审计只剩半截装载；
同一条码并发双装还会突破班次唯一。

## 决策
全局只贯彻 **架构 B：告警仍装载、落「待补目的地」待补码**。

- 缺目的地码的过机 **允许落账**，但状态为 `待补目的地`：写扫描行、**不进待路由桶、不可裁决**。
- 缺码事实写入 `scans.reject_reason`（值 `缺目的地码`）与审计流水，**可核且永不被静默抹掉**。
- 装载回执区分 `装载结果=待补码/成功`，并带 `可裁决` 与 `拒因`，绝不假装成功。
- 补码口 `POST /api/扫描/{id}/补码` 仅对 `待补目的地` 件开放；补码后同一行翻 `待路由`，
  此时才可裁决。补码清除拒因并留审计。
- 总览单独暴露 `待补目的地` 格；`待路由` 只数通过谓词的件；另做脏行自检 `脏行/脏行数`。

## 不采用架构 A（硬拒）的原因
A 口径下无目的地即整笔失败、不落扫描行，系统中不存在可补码对象，
无法满足需求明确要求的「补码前后裁决分叉」「缺码再装、补码后再裁决」「待补展示」。

## 不变量（全局不得混用另一套）
1. 读写共用同一谓词 `app.services.loading.can_enter_routing`：
   写侧装载/补码/裁决与读侧扫描册、待路由桶、总览全部重放它，禁止读侧另写判断。
2. 状态 `待补目的地` 永不进入待路由桶，裁决入口对其硬挡（拒因 `缺目的地码`）。
3. 装载在单连接 `BEGIN IMMEDIATE` 事务内完成（扫描行 + 审计同生共死），
   任一步失败整体回滚到装载前快照，不留无目的地却可裁决的脏行。
4. 班次内条码唯一由 `ux_scans_barcode_shift` 唯一索引兜底，并发双装一成一拒。

## 范围
仅覆盖缺目的地装载闸。路由裁决规则本身与口门闭口为独立需求，不在本 ADR 内变更。
