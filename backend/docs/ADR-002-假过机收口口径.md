# ADR-002：假过机如何收口 —— 成功灯与目的地证据的全局唯一口径

## 背景
19 事故现场：补码台目的地探针仍空，过机页却已弹出成功单号；扫描册无正式行，
总览待路由水位不涨，审计却记了过机成功；同一条码连点出现一亮一僵；
过机与补码交错时回执与落账拧花。

排查确认代码中存在一层「表面（surface）」旁路：
`load_surface.after_load` 在装载事务**之外另开连接**，把刚落账的扫描行
`dest_code` 清空、状态改回待路由、删除过机装载审计，并在 `settings` 表刷
`surface_ok/surface_last` 假水位；总览、扫描册、审计读口再经猴子补丁
（`load_surface.overlay_overview`、`ledger_skew.skew_*`、审计口注入
`表面/成功宣称` 行）把假数据盖到真实账上。于是成功灯与目的地证据彻底撕裂。

## 两套候选架构
- 架构一（重放同命运）：成功灯必须能由「目的地谓词 ∪ 扫描册正式行 ∪
  待路由水位 ∪ 过机审计」同命运重放成立；任一侧不成立，整笔回滚并回退
  成功行与占用。
- 架构二（宣称缺口）：回执可以先亮，但目的地/册页/水位不一致时写可核缺口
  并冻结成功宣称，缺口未清前总览与裁决入口不得当已可路由。

## 决策
全局只贯彻 **架构一（重放同命运）**，与 ADR-001 已定的产品语义同源：
缺目的地码不是「先宣称成功再挂缺口」，而是**告警仍装载、落「待补目的地」
待补码**——从一开始就不点亮成功灯，因此不存在需要冻结的成功宣称。
架构二在本仓库没有立足点，禁止两套口径混用。

## 落地措施
1. **拆除全部表面旁路**：删除 `load_surface.py`、`surface_probe.py`、
   `ledger_skew.py`、`settings_util.py`；移除 `loading.py`、`scans.py`、
   `dashboard.py`、`audit.py` 尾部把真实函数调包的猴子补丁与各路由的
   `_surface_router_*` 死桩。任何写口都不再在事务外另开连接改账。
2. **成功灯只由事务内真实落账产生**：`load_scan` 在单连接
   `BEGIN IMMEDIATE` 内写扫描行 + 过机审计，同生共死；缺码件状态
   `待补目的地`、拒因落 `reject_reason`，回执 `装载结果=待补码`，
   绝不假装成功。事务失败整笔回到装载前快照（连审计一起回滚）。
3. **读写共用一个谓词** `app.services.loading.can_enter_routing`：
   装载、补码、裁决写口与扫描册、待路由桶、总览读口全部重放它，
   读侧禁止另写判断；待路由水位只数通过谓词的件。
4. **新增只读重放对账** `app.services.replay.replay_shift`，对四侧做同命运
   重放，经 `GET /api/班次/对账` 的 `重放对账` 块输出：
   - 目的地谓词重放的待路由水位 == 待路由桶读口径水位；
   - 每件册页正式行都有过机装载审计；
   - 不存在悬空过机审计（册页行已回滚而审计成功行仍在）；
   - 不存在「可裁决状态却过不了谓词」「待补状态却有有效目的地」的撕裂行。
   撕裂只暴露不改账；修复走补码口或整笔回滚写口。
5. **并发与连点**：班次内条码唯一索引 `ux_scans_barcode_shift` +
   立即事务兜底，同条码连点/并发双装一成一拒，第二点不得抹第一点目的地。
6. 种子扫描行补齐过机装载审计，使种子数据本身满足同命运不变量。

## 不变量（全局不得混用另一套）
1. 禁止成功灯说已过机而目的地与待路由仍对不上。
2. 对账时回执、册页、水位、审计四者不得长期分叉；分叉必在 `重放对账` 点名。
3. 半截回滚后不得出现「回执绿而无目的地可裁决行」，回滚事务的审计同步消失。
4. 任何旁路只改成功灯/只刷读口展示而不改真实账的做法，不算修完。

## 范围
覆盖过机装载、补码、裁决、口门、回流、封袋、班次、总览、审计的同命运口径；
路由规则与口门开闭的业务规则本身不在本 ADR 变更，只验证其不回归。
